# ADR-2026-08-20: Hierarchical Adaptive Model Harness (HAMH)

Status: Proposed (wird mit Evidenzfortschritt sukzessive zu IMPLEMENTED —
analog zum v2-ADR, das vor dem Bau als kanonische Bauvorgabe dokumentiert und
danach am realen System verifiziert wurde). Entscheidungen sind H1..Hn.

## Kontext

Der AutoDev-Harness-v2 (ADR-2026-08-17, E1–E16) ist ein deterministischer
Control-Plane-Stack mit hart codiertem Provider/Modell-Paar
(`embedded` bzw. `lmstudio/huihui-qwen3.5-9b-abliterated`), einer statischen,
für alle Jobtypen identischen Tool-Policy (PLAN_TOOLS/BUILD_TOOLS) und ohne
jeglichen Mechanismus, um Prompt-/Kontext-/Tool-Strategien pro Modell oder
pro Aufgabe zu versionieren, zu bewerten oder deterministisch freizuschalten.

Der Bauauftrag „Hierarchical Adaptive Model Harness" (HAMH) verlangt, das
Harness selbst zum Gegenstand kontrollierter Evolution zu machen, ohne die
Kernprinzipien zu schwächen:

```text
LLMs ARE WORKERS. LLMs ARE NOT THE CONTROLLER. n8n = CONTROL PLANE.
```

HAMH darf den Controller nie ersetzen. Es ergänzt eine **zweite Ebene der
Selbstverbesserung**: die Control Plane bleibt deterministisch; was sich
evolutionär verändern darf, sind ausschließlich die *Harness-Zellen*
(Prompt-/Kontext-/Tool-/Editier-/Stop-Profile) unter harten Governance-Gates.

### Literatursplit (2026-08, Primärquellen)

Die Kernfrage „Shared Kernel + Model/Task-Zellen statt ein universelles
Harness oder ein unabhängiger Stack pro Modell" wird durch die Literatur
*gespalten* beantwortet — und genau daraus folgt die gewählte Architektur:

| Quelle | Aussage | Konsequenz für HAMH |
|---|---|---|
| One Recipe, Many Harnesses (2608.10178) | Geteiltes abstraktes Playbook lässt sich in einen **universellen Kern** übertragen; der Ökosystem-Vorteil entsteht erst durch **native Re-Evolution pro Zelle** | Stützt Shared Kernel (Layer A) + pro-Modell/pro-Aufgabe-Zellen (Layer B–E) |
| Self-Harness (2606.09498) | Harness ist **inhärent modellspezifisch**; 3-Stufen-Loop (Schwächen-Mining → minimale Vorschläge → regressionsvalidierte Akzeptanz) | Stützt pro-Modell-Model-Adapter/Model-Profile; verlangt minimal-invasive Kandidaten + Regressionsgate |
| Hierarchical Self-Improvement (2608.08466) | 3-Scope-Hierarchie (Task-Harness/Evolver/Meta-Evolver), **hot-swappable** Task-Harness, Backbone-Capability-Bound (Null-Gewinn jenseits der Backbone-Fähigkeit) | Stützt Task-Profile + **Capability-Bound-These**: CAPABILITY_FAILURE → bestehendes Routing/Eskalation statt Endlos-Evolution |
| HarnessCompass (2608.01918) | Beschränkt auf task-agnostische Edits + komponentenweise entkoppelte Optimierung; behauptet Cross-Model-Transfer | Transfer-Behauptung wird **nicht übernommen**; Zellen bleiben pro Modell versioniert |

## Entscheidungen

### H1. Shared Kernel + Model/Task-Harness-Zellen (kein Universal-Harness, kein Stack pro Modell)

Ein **einziges globales Shared Kernel** (Layer A, nicht modellevolvierbar)
trägt alle Kontroll- und Sicherheitsprimitiven. Darüber liegen
**pro-Modell-Adapter** (Layer B) und **versionierte Profile** (Layer C) sowie
**Task-Profile** (Layer D). Es wird weder ein universelles Allmodell-Harness
gebaut (widerspricht Self-Harness: Harness ist modellspezifisch) noch ein
unabhängiger DeepSeek-Stack (widerspricht One-Recipe-Many-Harnesses: der
universelle Kern ist bereits der v2-Control-Plane). Provider-/Modell-
agnostisch ab Tag 1; erster echter Referenzpfad ist DeepSeek V4 Flash.

### H2. Schichttrennung A–E, gemappt auf Bestand

| Schicht | Inhalt | Bestand | Neu |
|---|---|---|---|
| **A Shared Kernel** (global, NICHT modellevolvierbar) | Controller-Autorität, Routing, Provider-Auswahl, globale Contracts, Security, MCP-Allow/Deny, Budgets, Retry/Eskalation, Verifikation, Audit-Events, Git-Safety, Produktions-Sentinels, Rollback, Promotions-Autorität | n8n-Control-Plane (E1–E9, E16), Contracts (E8), Deterministische Verifikation (E9) | nur Promotions-Autoritäts-Gate (mechanisch, deterministisch) |
| **B Model Adapter** (Provider/API-Semantik, KEIN Prompt-Profil) | exakte Modell-ID, Thinking an/aus, Reasoning-Effort, Tool-Call-Semantik, Multi-Turn-State, Context-Fenster, Max-Output, Cache-Telemetrie, Provider-Fehlertypen, Rate/Concurrency | LM-Studio-Provider-Overlay (`local_llm`) de facto | `deepseek_adapter.py` (reine Semantik, keine Live-Calls) |
| **C Model Profile** (versionierbar) | Reasoning-Strategie, Kontext-Präferenzen, Tool-Schnittstellen-Präferenzen, Editier-Strategie, Stop-Verhalten, Failure-Fingerprints, bevorzugte Interaktion, cache-freundliches Kontext-Layout, Task-Komplexitätsschwellen | `_agent_md()` statisch (YAML) | `profiles.py` ModelProfile |
| **D Task Profiles** | research/plan/build/review (verify bleibt deterministisch) | statische PLAN/RESEARCH/BUILD_TOOLS | `profiles.py` TaskProfile (alle vier initial identisch = geteiltes Baseline) |
| **E Execution + Evaluation + Evolution + Promotion** | Trajektorien-Telemetrie, deterministische Evaluations-Suite, Candidate-Evolution-Sandbox, deterministische Promotion | Ledger + Batch + Verifier (E4, E13, E9) | `evolution.py`, `telemetry.py`, `task_suite.py` |

**Explizit NICHT gebaut** (Anti-Overengineering): kein neues Workflow-
Framework, kein zweiter Router, kein zweiter MCP-Stack, kein zweiter Verifier,
keine zweite Retry-/Queue-/Datenbank-Instanz. Alle Primitiven werden aus dem
v2-Bestand wiederverwendet.

### H3. Resolver im Adapter (eine Python-Implementierung, deterministisch)

Der Harness-Resolver lebt als einzige, unit-testbare Python-Implementierung im
Adapter (`runtime/hamh/resolver.py`). n8n reicht `provider/model/
model_revision/task_class/runtime_mode` als **rückwärtskompatible optionale
Felder** an `POST /v1/jobs` durch; der Adapter löst das Harness beim Dispatch
auf und schreibt `resolved_harness_id/version/fingerprint` in Job-Record,
Ledger und ein Per-Run-Resolution-Artefakt zurück. Die Controller-Autorität
bleibt unverändert: n8n entscheidet weiterhin über Jobs und Backend; der
Resolver entscheidet nur über die *Harness-Konfiguration innerhalb* eines
vom Controller freigegebenen Jobs.

Begründung: Es gibt genau eine Stelle, an der das Job-Record und das Ledger
entstehen (Adapter `_dispatch`/`new_job`/`finalize_job`). Eine Resolver-Logik
in n8n würde den deterministischen Kern duplizieren und die JS/Py-Äquivalenz-
Matrix (bereits 27/27 Tests) unnötig belasten. Unbekanntes Modell → expliziter
deterministischer Baseline-Fallback (kein Crash, kein Zufall).

### H4. Harness-Registry als JSON-Datei (State-Machine, autoritätsgesteuertes promote)

Registry ist ein **JSON-Datei-gestützter Store** (im bestehenden State-Verzeichnis,
kein neues DBMS): `registry.py` hält Einträge, Zustandsmaschine und ein
`promote()`-Gate. Zustände: DRAFT/CANDIDATE/SHADOW/CANARY/ACTIVE/RETIRED/REJECTED.
ACTIVE wird **ausschließlich** über den autorisierten Promotionspfad erreicht
(EVOLVER_CAN_PROMOTE=NO); ein Kandidat kann sich nie selbst auf ACTIVE setzen.
Autorität = deterministischer Verifier + deterministische Gates (kein LLM-Urteil),
konsistent mit E9.

### H5. Kanonische Harness-Identität + stabiler Fingerprint

`provider/model/model_revision/runtime_mode/task_class/harness_version` bilden
die kanonische Identität; der Fingerprint nutzt exakt die bestehende kanonische
Hash-Strategie aus `runtime/contracts/fingerprint.py` (sortierte Schlüssel,
`ensure_ascii`, SHA-256, x-metadata exkludiert). Jede semantisch relevante
Änderung an einem Profil ändert den Fingerprint (Isolationstest G).

### H6. DeepSeek-Model-Adapter (deepseek-v4-flash, offizielle API-Semantik)

Der Model Adapter `deepseek_adapter.py` implementiert ausschließlich
**Semantik + Contract-Tests, keine Live-Netzwerkaufrufe**. Verifizierte
Live-API-Fakten (api-docs.deepseek.com, 2026-08-20):

- Modell-IDs heute: nur `deepseek-v4-flash` (DeepSeek-V4-Flash-0731) und
  `deepseek-v4-pro` (DeepSeek-V4-Pro-0813). `deepseek-chat`/`deepseek-reasoner`
  seit 2026-07-24 RETIRED. **Reasoning ist ein Modus, kein Modell.**
- Thinking: `thinking: {"type": "enabled"|"disabled"}` (Default enabled);
  `reasoning_effort`: `low`|`high`|`max` (Default high; medium/xhigh → high).
  `temperature`/`top_p` sind im Thinking-Modus stille No-Ops.
- **Tool-Turns:** `reasoning_content` MUSS in allen Folge-Requests
  zurückgegeben werden, wenn `tools` gesetzt ist, sonst HTTP 400.
  Non-Tool-Turns: `reasoning_content` wird ignoriert.
- Tools: nur `type: function`, max 128; `tool_choice` none|auto|required|named;
  Strict-Mode ist Beta (verlangt `https://api.deepseek.com/beta`, alle
  Funktionen `strict:true`, alle Object-Properties `required` +
  `additionalProperties:false`; String-`minLength`/`maxLength` nicht unterstützt).
- Chat Prefix Completion (Beta, `/beta`): letzte Message `role:assistant` mit
  `prefix:true`; `reasoning_content` als CoT-Eingabe.
- Context 1M, Max-Output 384K (beide Modelle); kein dokumentierter Default
  für `max_tokens`.
- Caching: automatisches Prefix-Caching (Default an); Telemetrie über
  `usage.prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`; best-effort.
- Fehler **nur nach HTTP-Status** (keine String-Fehlercodes): 400 Invalid
  Format, 401 Auth, 402 Insufficient Balance, 422 Invalid Parameters,
  429 Rate Limit, 500 Server Error, 503 Server Overloaded; `finish_reason`
  enthält `insufficient_system_resource`.
- Concurrency (Account-Level): flash 2500, pro 500; optionaler `user_id`-Param
  (Isolation); 10-Min-Keep-Alive-Cap.
- Endpunkte: `https://api.deepseek.com` (OpenAI-Format), `/anthropic`
  (Anthropic-Format), `/beta` (strict/prefix/FIM). Auth: `Authorization: Bearer`.
- **Namenskollision:** „DeepSeek Harness" ist inzwischen ein offizielles,
  separates DeepSeek-Produkt (Developer Preview). HAMH-Doku verwendet den
  nackten Namen „DeepSeek Harness" niemals; immer „HAMH" bzw.
  „DeepSeek-Model-Adapter".

### H7. Tool-Architektur: effective_tools ⊆ controller_allowed_tools

Fähigkeit (was darf der Agent) und Präsentation (wie wird es dem Agent
dargeboten) sind getrennt. Ein Task-Profil kann Werkzeuge nur **einschränken**,
nie erweitern; die Controller-Allowlist (PLAN_TOOLS/BUILD_TOOLS aus dem
Shared Kernel) ist die obere Schranke (Isolationstest D). Strukturierte
(Low-Level-)Schnittstellen sind zulässig, aber nur wenn evidenzgetrieben
evaluiert (vgl. Devil-in-the-Interface).

### H8. Kontext-Architektur: stabil vs. variabel, cache-freundlich, provider-nah

Stabiler Kontext (System-/Anweisungsteil) wird von variablem Kontext
(aufgabenspezifisch) getrennt, um Prefix-Caching zu maximieren. Die
cache-freundliche Anordnung ist **Provider-Level-Semantik** (Layer B/C),
nicht Teil des Shared Kernels. Cache-Hit/Miss-Telemetrie wird in die
Trajektorie aufgenommen (Layer E).

### H9. Adaptive Thinking als Profilvariable

Thinking (an/aus) und Reasoning-Effort sind Profilvariablen (Layer C). Die
Testmatrix misst `einfach/komplex × thinking/non-thinking` gegen: verifizierten
Erfolg, First-Pass, Latenz, Token-Kosten, Tool-Calls, Retries, Eskalationen.
Keine Standardpräferenz ohne Evidenz.

### H10. Failure-Taxonomie als ERWEITERUNG (keine Duplikation)

Neue Meta-Klassen `HARNESS_FAILURE`/`EXECUTION_FAILURE`/`STRATEGY_FAILURE`/
`CAPABILITY_FAILURE` werden **auf die bestehenden Adapter-Fehlerklassen
gemappt** (siehe `hamh-spec.md` §Failure-Taxonomie), nicht ersetzt.
`CAPABILITY_FAILURE` führt in das bestehende Routing/Eskalations-Leiter
(RETRY_DENIED_* → SPLIT), **kein Endlos-Evolutions-Loop** (Capability-Bound).

### H11. Trajektorien-Telemetrie (metadata-first, ohne sensitive Reasoning-Inhalte)

Trajektorie = run_id/model/provider/model_revision/harness_id/harness_version/
harness_fingerprint/task_class/runtime_mode/context_volume/tool_calls/
tool_failures/retry_count/escalation/token_usage/cache_hit_tokens/
cache_miss_tokens/latency/verification_result/failure_class/final_result.
Es wird **kein** sensitive `reasoning_content` persistiert (Privacy by Default,
E13 fortgeschrieben). Builder `telemetry.py` erzeugt die Records passend zu den
Ledger-Feldern.

### H12. Evolutions-Governance-Gates (propose/test-only)

Pipeline: Produktions-Trajektorien → Schwächen-Mining → Hypothese → minimale
Kandidaten-Modifikation → Kandidat → Evaluation → Regression → Holdout →
Shadow → Canary → autorisierte Promotion. Autoritäts-Gates:

```text
EVOLVER_CAN_PROPOSE = YES
EVOLVER_CAN_TEST    = YES
EVOLVER_CAN_PROMOTE = NO
EVOLVER_CAN_CHANGE_GATES   = NO
EVOLVER_CAN_CHANGE_HOLDOUT = NO
```

Eine Komponente pro Experiment. Evaluation trennt EVOLUTION/TRAIN,
VALIDATION, HOLDOUT; ein **Leakage-Sentinel** ist Pflicht. **Matched-Compute-
Kontrolle**: A = aktuelles Harness, B = Kandidat, C = aktuelles + äquivalentes
Zusatzbudget. B muss A schlagen UND der Effekt darf nicht durch C erklärbar
sein, sonst `HARNESS_VALUE=NOT_PROVEN` (Antwort auf „Rethinking Harness
Evolution").

### H13. Ehrliche Evidenz-Policy

`DEEPSEEK_LIVE_PROOF=NOT_RUN` (kein Credential vorhanden). Value-Beweis über
Live-Modelle ist in diesem Lauf **nicht möglich**; erwarteter ehrlicher
Endzustand ist `AMBER_HAMH_VALUE_NOT_PROVEN`. Foundation/Governance können
GREEN sein, wenn die deterministischen Tests (Isolation A–H, Resolver,
Registry-Autorität, Leakage, Matched-Compute, Capability-Klassifikation) grün
sind. Keine erfundenen Ergebnisse; keine hart-codierten Pseudo-Beweise.

### H14. Git-Disziplin

Fremde, untracked Arbeit `evidence/backup/v3-backup-20260819/` (GHIW-Backups)
wird **nicht angefasst und niemals committed**. Workflow-Änderungen erfolgen
**ausschließlich über den Generator** (`generate_workflows_v2.py`), nie durch
Handeditieren exportierter JSONs. Regeneration der JSON-Exporte lokal; **kein
Redeploy** auf das Live-n8n in diesem Lauf (Produktionsänderung = Runbook-
Schritt mit Freigabe). Kein Git-Remote → Evidenz-READMEs sind Source of Truth.

### H15. Adapter-Naht (rückwärtskompatibel)

`_dispatch`/`do_POST` akzeptieren optionale `provider/model/model_revision/
task_class`; Resolver wird beim Dispatch konsultiert; Harness-Felder landen in
Job-Record + Ledger-Subset. Provider/Model bleiben Observability- und
Profil-Inputs; **Backend-Routing bleibt unberührt** (VALID_BACKENDS unverändert).
Minimaler dokumentierter Bugfix in der Naht: `_opencode_sem` (Zeilen ~425/436/449)
ist referenziert, aber nie definiert → jeder echte opencode-Dispatch würde
`NameError` werfen; wird als `_opencode_sem = threading.BoundedSemaphore(1)`
nachgezogen (Serialisierung pro Backend, wie in Phase-D-Mitigation vorgesehen).

### H16. Klassifikations-Optionen

`GREEN_HAMH_FOUNDATION_OPERATIONAL` / `GREEN_HAMH_DEEPSEEK_V4_FLASH_RUNTIME_PROVEN`
/ `GREEN_HAMH_EVOLUTION_GOVERNANCE_PROVEN` / `GREEN_HAMH_VALUE_PROVEN` /
`AMBER_HAMH_VALUE_NOT_PROVEN`. In diesem Lauf erreichbar: Foundation/Governance
GREEN (deterministisch beweisbar), Value AMBER (ehrlich, mangels Live-Modellen).

## Konsequenzen

- **Einfacher:** Model-/Task-Profile versionierbar und rollback-fähig;
  Provider-Wechsel ohne Controller-Umbau; deterministische, testbare
  Harness-Auflösung; Evolution unter hartem Governance ohne Selbst-Promotion.
- **Schwerer:** Zwei neue Contracts und ein kleines Paket `runtime/hamh/`
  müssen gepflegt werden; die Promotionskette (DRAFT→ACTIVE) ist bewusst
  langsam und gate-gebunden; Value-Beweise bleiben bis zur Bereitstellung
  echter Provider-Credentials ehrlich „nicht erbracht".
- **Neue Artefakte:** `runtime/hamh/{registry,resolver,profiles,taxonomy,
  evolution,telemetry,deepseek_adapter}.py`; Contracts
  `hamh.harness.v1` + `hamh.resolution.v1`; Tests unter
  `evidence/tests/hamh/`; Docs `docs/architecture/hamh-spec.md` (+ später
  `docs/operations/hamh.md`); Evidenz unter `evidence/phase-*-hamh/`.
- **Unverändert (Invarianten):** CONTROLLER_AUTHORITY, ROUTING_AUTHORITY,
  RETRY_ESCALATION_SEPARATION, MCP_SECURITY_BOUNDARY, PRODUCTION_SENTINELS,
  VERIFIER_AUTHORITY, AUDITABILITY, ROLLBACK. MODEL_SELF_PROMOTION/
  SECURITY_CHANGE/ROUTING_CHANGE bleiben DENIED.
- **Regression:** Bestehende v2-Tests (26 Contracts + 27 Äquivalenz + 30
  Adapter + 9 Control-Plane) bleiben unverändert grün; HAMH ergänzt, ersetzt nicht.
